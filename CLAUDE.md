# Правила проекта: React 19, веб-сайт и будущие мобильные приложения

Версия: 1.2. Дата: 23 октября 2026 года.

## 1. Назначение и статус решений

Документ определяет правила разработки небольшого или среднего коммерческого проекта: публичные страницы, каталог, карточки товаров или услуг, корзина, формы, оформление заказа и при необходимости личный кабинет. Ориентир по пользовательским сценариям — [hongkong38.ru](https://hongkong38.ru/) и https://krasnoyarsk.yobidoyobi.ru/. Это ориентир по составу функций, а не требование копировать его код, дизайн или техническую платформу.

Этап 1 — адаптивный сайт для телефонов и компьютеров. Этап 2 — приложения Android и iOS с переиспользованием веб-интерфейса: Android WebView и iOS WKWebView. Телевизоры в текущий перечень целевых устройств не входят. При добавлении ТВ потребуется отдельный профиль совместимости, управления пультом и производительности.

Цель — быстро выпускать понятный, надежный и достаточно быстрый продукт. Ни документ, ни библиотека не гарантируют отсутствие переделок или уязвимостей. Мы уменьшаем их вероятность через раннее выяснение ограничений, простую архитектуру и проверяемые критерии.

Термины:

- **Обязательно** — требование для приемки. Отступление нужно явно согласовать и записать с причиной.
- **По умолчанию** — рекомендуемый вариант, который можно заменить обоснованным решением.
- **По необходимости** — инструмент подключается при появлении конкретной задачи.
- **Блокирующий вопрос** — без ответа высок риск выбрать неверную архитектуру, нарушить безопасность или изменить согласованное поведение.

Подтверждено: React 19, Zustand, простая структура, стили рядом с компонентом, телефоны и компьютеры, мобильные оболочки после веб-версии. TypeScript и CSS Modules рекомендованы этим документом. SEO, серверная часть, способ размещения, авторизация, платежный провайдер и способ распространения приложений требуют решения перед соответствующей реализацией.

## 2. Короткий набор обязательных правил

1. Сначала понять задачу, явно назвать существенные допущения и определить проверяемые критерии приемки; затем писать код.
2. До изменений прочитать `AGENTS.md`, `CLAUDE.md`, `CHANGES.md` и найти похожую реализацию.
3. Прямо указывать на слабые решения пользователя и предлагать более простой обоснованный вариант.
4. Одна ответственность у компонента, функции и модуля. Размер файла — сигнал для анализа, а не самоцель.
5. Локальные данные остаются локальными; Zustand содержит общее клиентское состояние; серверные данные имеют одного владельца кеша.
6. Подписываться на нужные поля Zustand, сохранять ссылки на неизмененные части данных.
7. Переиспользовать общую логику и UI, не создавать универсальные компоненты с десятками режимов.
8. Оптимизировать по измерениям. Виртуализация, мемоизация и дополнительные библиотеки требуют причины.
9. Публичный интерфейс не является границей безопасности. Все права и коммерчески значимые значения проверяет сервер.
10. Сразу учитывать будущие WebView/WKWebView, но не реализовывать заранее ненужные нативные функции.
11. Проверять негативные сценарии и связанные участки, а не только успешный путь новой функции.
12. Каждое изменение связывать с задачей; завершать работу проверками, обновлением документации и честным отчетом о непроверенном.
13. Для существенных кодовых задач проводить независимое ревью со свежим контекстом; нескольких исполнителей подключать к четко разделяемым частям работы. Итог проверять после интеграции.

## 3. Выбор основы до начала разработки

### 3.1. Что выяснить первым

Перед созданием приложения зафиксировать краткий паспорт проекта:

- Какие страницы должны попадать в поиск и отдавать содержательный HTML при первом запросе?
- Какие роли и сценарии существуют: посетитель, покупатель, оператор, администратор?
- Есть ли готовое API? Кто отвечает за цены, доступность, доставку, платежи и авторизацию?
- Как часто обновляется каталог? Есть ли разные филиалы, цены, остатки и часовые пояса?
- Какие объемы ожидаются сейчас и через год: товары, категории, одновременные пользователи?
- Где размещается сайт: только статические файлы или доступен серверный runtime?
- Приложения будут распространяться через магазины или иным способом? Что им требуется помимо сайта?
- Какие браузеры, версии ОС и слабое устройство входят в обязательную поддержку?

Не спрашивать пользователя о том, что можно достоверно выяснить из проекта или документации. Не выдавать предположения за подтвержденные требования.

### 3.2. Правило выбора рендеринга

React 19 не означает автоматически ни Vite, ни Next.js. Сначала выбрать способ доставки страниц и совместимость с будущей мобильной упаковкой.

| Условия | Предпочтительный вариант | Что проверить заранее |
| --- | --- | --- |
| Приложение, где SEO не является основным каналом, API отдельно | Vite + React 19 + React Router | Прямые ссылки, обновление вложенных маршрутов, серверная отдача SPA, будущая упаковка в Capacitor |
| Публичный каталог, важен готовый HTML для поиска и предпросмотра ссылок | React-фреймворк; основной кандидат — Next.js с SSG/SSR по страницам | Хостинг, кеширование, актуальность каталога, стоимость клиентского JavaScript и способ сборки мобильного интерфейса |
| Нужен один статический комплект для сайта и оболочек, каталог известен на сборке | Проверить пригодность Next.js static export либо выбрать Vite при допустимой клиентской загрузке контента | Все маршруты, обновление каталога, ограничения export, маршрутизация и авторизация внутри оболочек |

Для сайта, похожего на пример, предварительная рекомендация при важном SEO — SSG для подходящих публичных страниц и SSR там, где нужна актуальность на запрос. Персональные данные не включать в общий кеш. Для каждого источника данных задать допустимый возраст и способ обновления.

Серверные возможности Next.js нельзя просто поместить внутрь локальной мобильной сборки. Если сайт использует их, заранее выбрать одно из решений: совместимый статический профиль или отдельная клиентская точка входа с общими функциональными модулями. Разделять приложения и вводить workspace только при подтвержденной необходимости. Не обещать «одну сборку для всего» без проверки. Ограничения описаны в [Next.js static export](https://nextjs.org/docs/app/guides/static-exports).

До окончательного выбора провести небольшой технический эксперимент: публичная карточка → корзина → тестовая авторизация → пробный запрос API из Android/iOS-оболочки. Это проверка архитектурных рисков; сами приложения и их публикация остаются вторым этапом. Если iOS сейчас недоступен, явно зафиксировать непроверенную часть.

### 3.3. Правило простоты

По умолчанию один репозиторий и одно веб-приложение. Не вводить микрофронтенды, микросервисы, собственный DI-контейнер, универсальный конструктор форм или многослойную архитектуру без задачи, которая их оправдывает. Не переписывать существующий проект на предпочтительный стек только ради соответствия шаблону.

Реализовывать минимальное законченное решение согласованной задачи. Не добавлять незапрошенные функции, настройки, режимы и точки расширения ради гипотетического будущего. Для новой абстракции объяснить пользу сейчас: понятная ответственность, граница безопасности, изоляция платформы, упрощение проверки или устойчивое переиспользование. Одно использование само по себе не запрещает полезную границу; правила выделения общих компонентов — в разделе 6.

Не добавлять защитные ветки для состояний, невозможность которых обеспечена проверяемым контрактом. При этом сбои сети, поврежденное хранилище, отказ разрешения и недоверенные внешние данные — реальные сценарии, их обработку сохранять. Если инвариант не доказан, не объявлять сценарий невозможным ради сокращения кода.

Перед завершением проверить: можно ли решить ту же задачу существенно проще без потери поведения, безопасности и проверяемости? Если да — упростить. Количество строк не является самостоятельным критерием: короткий, но неочевидный код не лучше понятного решения.

## 4. Технологии и зависимости

| Область | Решение | Условие применения |
| --- | --- | --- |
| Интерфейс | React 19 и совместимый React DOM | Поддерживаемый стабильный релиз ветки 19 с актуальными исправлениями безопасности; версии согласованы |
| Типизация | TypeScript, `strict` | По умолчанию для исходников; `unknown` на недоверенных границах вместо произвольного `any` |
| Общий клиентский state | Zustand | Корзина, общие настройки и действительно разделяемое UI-состояние |
| Данные API в браузере | TanStack Query | При необходимости клиентского кеша, повторного использования запросов, мутаций и обновлений |
| Схемы внешних данных | Zod | Входы API, формы, сохраненные данные, конфигурация и сообщения bridge |
| Формы | React Hook Form + адаптер Zod | Составные формы с зависимостями и валидацией; простая форма может обойтись средствами React и браузера |
| Стили | CSS Modules + CSS custom properties | По умолчанию; SCSS только при реальной пользе, без параллельной системы стилизации |
| Сложные UI-примитивы | Radix Primitives | Диалоги, выпадающие меню и другие виджеты, где важны фокус и доступность; импортировать нужные части |
| Классы | `clsx` | Если условные классы заметно упрощают JSX |
| Длинные списки | TanStack Virtual | Только после подтверждения необходимости виртуализации |
| Анимации | CSS transitions/animations | Motion или другая библиотека — для конкретного сложного сценария после оценки стоимости |
| Тесты | Vitest, React Testing Library, Playwright | Чистая логика и компоненты; сквозные браузерные сценарии. Учитывать ограничения тестирования серверных компонентов выбранного фреймворка |
| Контроль качества | ESLint, TypeScript, форматтер | Одна конфигурация на проект, обязательные проверки в CI |
| Мобильная упаковка | Capacitor — основной кандидат | После проверки нужных плагинов, текущих требований Android/iOS и модели загрузки приложения |

Это меню решений, а не команда установить все сразу. Для одной задачи не использовать одновременно несколько роутеров, HTTP-клиентов, form-библиотек или менеджеров серверного кеша. При Next.js использовать его роутер; React Router поверх него не добавлять.

Если серверный фреймворк уже полностью обеспечивает загрузку конкретных данных, не добавлять для них TanStack Query автоматически. При SSR и клиентском обновлении определить передачу начальных данных и единого владельца клиентского кеша, чтобы не получить двойную загрузку.

React Compiler рассмотреть для нового проекта при совместимости стека. Это отдельная настройка сборки, а не функция, автоматически включенная фактом использования React 19. Проверить, что компиляция работает; не добавлять `memo`, `useMemo` и `useCallback` повсюду. См. [React Compiler](https://react.dev/learn/react-compiler) и [установку](https://react.dev/learn/react-compiler/installation).

Новая зависимость требует краткого объяснения: какую задачу решает, почему недостаточно платформы или уже установленного пакета, совместима ли с React 19/SSR/WebView, поддерживается ли, какая лицензия и вклад в production-сборку. Точные версии фиксировать lock-файлом; документацию проверять для установленной версии. Обновления делать отдельно от функциональных изменений, кроме необходимых исправлений безопасности.

## 5. Простая структура проекта

```text
src/
  app/                         # вход приложения, провайдеры, маршруты
  screens/                     # сборка экранов из функциональных модулей
    CatalogScreen/
      CatalogScreen.tsx
      CatalogScreen.module.css
  features/
    catalog/
      api/                     # запросы каталога и ключи кеша
      model/                   # типы, схемы, чистая логика
      ui/
        ProductCard/
          ProductCard.tsx
          ProductCard.module.css
          ProductCard.test.tsx
      index.ts                 # небольшой публичный API модуля
    cart/
    checkout/
  shared/
    ui/                        # Button, Dialog, Input — без знаний о заказах
    api/                       # транспорт и общая обработка ошибок
    contracts/                 # общие контракты данных, если они нужны
    platform/                  # адаптеры браузера и будущих оболочек
    lib/                       # небольшие функции общего назначения
    styles/                    # токены и базовые стили
  server/                      # только если выбран серверный runtime
public/
tests/e2e/
docs/decisions/                # только значимые архитектурные решения
AGENTS.md
CLAUDE.md
PROJECT_RULES.md
CHANGES.md
README.md
```

Правила структуры:

- Создавать каталоги по необходимости, без пустых заготовок всех будущих функций.
- У компонента есть своя папка; стили, локальные тесты и вспомогательные файлы лежат рядом. Если собственных стилей или тестов нет, пустые файлы не нужны.
- `app` содержит интеграцию, `screens` — композицию экрана, `features` — предметные функции, `shared` — независимые общие средства.
- При Next.js файловые маршруты находятся в `app`, а переиспользуемые экраны — в `screens`. Не создавать параллельно папку `pages` случайным образом.
- Направление зависимостей: `app → screens → features → shared`. Нижний уровень не импортирует верхний; циклические импорты запрещены.
- Прямые зависимости одной feature от внутренностей другой запрещены. Обмен — через композицию экрана, явно выделенный общий контракт или согласованный публичный API. Общий предметный модуль выделять только при реальной необходимости.
- Не переносить бизнес-логику в `shared/lib` только потому, что она используется дважды. Имя папки должно объяснять назначение.
- Клиентский код не импортирует серверные модули, секреты, доступ к базе. Использовать защиту границы, доступную в выбранном фреймворке, и проверять импорты линтером.
- `index.ts` — небольшой публичный интерфейс feature. Не делать глобальные barrel-файлы, экспортирующие весь проект. Внутри модуля не импортировать его собственный barrel.
- Существующий стиль имеет приоритет перед косметическими предпочтениями. Не переименовывать и не форматировать несвязанные файлы в рамках задачи.

## 6. Компоненты, композиция и переиспользование

Компонент решает одну понятную пользовательскую или визуальную задачу. Отдельная функция решает одну логическую задачу. Разделять отображение, сетевой транспорт и сложные бизнес-вычисления. Не выносить каждую строку в отдельный hook: дополнительная сущность должна делать код понятнее.

Ориентир для ревью — компонент около 150–250 строк или функция, которую трудно объяснить одним предложением. Это повод проверить ответственность и сложность, а не жесткий лимит. Короткий компонент с множеством взаимосвязанных режимов тоже может быть плохим.

Правило повторения: при третьем похожем использовании обязательно оценить общую часть. Выносить ее, если совпадают смысл, правила поведения и причины будущих изменений. Совпадение верстки само по себе недостаточно. Небольшое осознанное дублирование лучше абстракции с множеством исключений. Стабильные примитивы вроде кнопки допустимо выделять с первого использования.

Для модальных окон:

- Одна общая оболочка `Dialog`: слой, контейнер, размеры, заголовок, фокус, закрытие, scroll lock и доступность.
- Разное содержимое передается через композицию: `children`, заголовок, footer и небольшое число явных вариантов.
- `ProductDialog`, `AddressDialog`, `ConfirmDialog` могут быть отдельными предметными компонентами поверх общей оболочки. Их бизнес-логика не попадает в базовый `Dialog`.
- Не создавать `UniversalModal` с флагами `isProduct`, `isPayment`, `isAddress` и десятками несвязанных свойств.
- Локальный диалог открывается локальным состоянием. Глобальный менеджер диалогов нужен только для подтвержденных межэкранных сценариев; в persisted state не хранить JSX, функции и callbacks.

Базовый Dialog обеспечивает начальный фокус, удержание Tab внутри окна, доступное название, Escape и возврат фокуса к логичному элементу после закрытия. Если исходный элемент исчез, нужен разумный запасной вариант. Не делать фон интерактивным при открытой модалке. На телефонах отдельно проверить клавиатуру и прокрутку. Основа: [WAI-ARIA Dialog Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) и [Radix Dialog](https://www.radix-ui.com/primitives/docs/components/dialog).

Публичные props должны быть небольшими и типизированными. Взаимоисключающие режимы выражать типами, а не независимыми boolean-флагами. Общий UI не знает об API, заказах и глобальном store, если это не его явно заявленная ответственность.

## 7. Состояние: один владелец каждого значения

| Данные | Где хранить | Пример |
| --- | --- | --- |
| Временное состояние одного компонента | `useState` / `useReducer` | Открытое локальное меню, вкладка, развернутый блок |
| Значения и ошибки формы | Локально или React Hook Form | Телефон, комментарий к заказу, адрес до отправки |
| Состояние, которым делятся разные части интерфейса | Zustand | Клиентская корзина, выбранный филиал, настройки |
| Серверные данные | Кеш загрузчика фреймворка / TanStack Query по выбранной схеме | Каталог, профиль, статус заказа |
| Навигация, которую нужно сохранять в ссылке | URL и роутер | Категория, сортировка, примененные фильтры, страница |
| Вычисляемые значения | Чистая функция или selector | Число позиций, предварительная сумма, отфильтрованный список |

Не копировать одни и те же данные в Zustand, Query и локальный state «для удобства». Исключение — явно отделенный редактируемый черновик с правилами сохранения и отмены. URL-параметры валидировать; секреты и персональные данные в URL не помещать.

### 7.1. Правила Zustand

1. Разделять store по ответственности, а не по каждой переменной. Не делать один store на все приложение.
2. В React подписываться на нужное значение через selector. Вызов store без selector в обычном UI — повод для исправления.
3. Если выбираются несколько полей через новый объект или массив, использовать отдельные подписки либо `useShallow` при подходящей поверхностной семантике. Сложные вложенные результаты должны иметь стабильные ссылки; `useShallow` не заменяет эту работу.
4. Изменять данные иммутабельно, сохраняя ссылки на неизмененные элементы. Не пересоздавать все записи ради изменения одной.
5. Логику перехода состояния держать в действиях store или чистых функциях модели. Обновление на основе предыдущего состояния должно использовать актуальное предыдущее значение.
6. Не хранить одновременно исходные данные и легко вычисляемые итоги без подтвержденной причины и механизма согласования.
7. При большом списке родитель выбирает стабильные идентификаторы, строка — свои данные по идентификатору. Не передавать весь store каждой карточке.
8. Не использовать `getState()` вместо реактивной подписки для отображаемых значений. Он подходит для императивного чтения вне рендера.
9. Scroll-позиции на каждый кадр, координаты жеста и анимационные значения по возможности держать вне React state и глобального store.

Селектор ограничивает обновления от store, но не отменяет рендеры от родителя, props и context. Для списка отдельно проверить стабильность props и границы компонентов. Нельзя обещать «изменился один товар — технически рендерится ровно один компонент» без профилирования. См. [Zustand selectors и useShallow](https://zustand.docs.pmnd.rs/learn/guides/prevent-rerenders-with-use-shallow.html).

### 7.2. Сохранение и восстановление

- Persist включать выборочно, с разрешенным списком полей. Корзина хранит идентификаторы, выбранные опции и количества; сохраненная цена не является подтвержденной серверной ценой.
- Добавлять версию схемы, миграцию и безопасный сброс поврежденных данных. Обрабатывать отказ storage и превышение квоты.
- Не сохранять токены, платежные данные, адреса и телефон в обычный persisted store по умолчанию. Для пользовательского черновика с персональными данными отдельно решить срок хранения, согласие, удаление и необходимость такой функции.
- Для нескольких вкладок определить политику: синхронизация, разрешение конфликтов или явное ограничение. Не допускать бесконечной взаимной записи.
- При SSR не создавать общий изменяемый пользовательский store на серверный процесс. Изоляция на запрос/дерево и одинаковое начальное состояние защищают от утечек и ошибок гидратации. Чтение localStorage — только на клиенте, с предсказуемым состоянием до восстановления. См. [Zustand и Next.js](https://zustand.docs.pmnd.rs/learn/guides/nextjs.html).
- При выходе очистить приватные кеши и пользовательские данные; отдельно определить судьбу гостевой корзины и правила ее объединения после входа.

## 8. React, рендеры и побочные эффекты

Приоритет: правильная модель данных → локальность состояния → узкие подписки → понятная композиция → измерение → точечная оптимизация.

- Рендер должен быть чистым: без запросов, записей в storage, таймеров и мутаций внешних данных.
- Производные значения считать при рендере или в selector. Не синхронизировать одно состояние с другим цепочками `useEffect`.
- Обработку пользовательского действия запускать из обработчика или механизма мутации, а не косвенно через цепочку эффектов.
- Эффекты использовать для синхронизации с внешними системами. Соблюдать зависимости; очищать подписки, listeners, observers и таймеры. Устаревшие сетевые результаты не должны перезаписывать актуальные.
- Не отключать Strict Mode ради скрытия двойного запуска эффектов в разработке. Исправлять очистку и повторную инициализацию; не запускать создание заказа из mount-эффекта.
- Не добавлять мемоизацию «на всякий случай». С Compiler сначала проверить его работу; без него точечно мемоизировать действительно дорогие узлы по профилю.
- Не применять глубокое сравнение всего дерева props для маскировки нестабильных данных. Не считать `useMemo` гарантией корректности или постоянного хранения.
- `useTransition` и `useDeferredValue` могут улучшать отзывчивость, но не уменьшают объем вычислений и не заменяют отмену запросов, debounce или виртуализацию.
- Большие изменяемые объекты в Context не использовать как замену селективным подпискам. Context подходит для стабильных зависимостей и ограниченных провайдеров.
- Для элементов списка использовать стабильные предметные ключи, а не случайные значения и не индекс в изменяемом списке.
- Серверные компоненты и браузерные модули не смешивать. При SSR интерактивные границы делать небольшими; не переносить весь layout на клиент ради одной кнопки.

Обоснование: [React об эффектах](https://react.dev/learn/you-might-not-need-an-effect), [useMemo](https://react.dev/reference/react/useMemo), [серверные и клиентские компоненты Next.js](https://nextjs.org/docs/app/getting-started/server-and-client-components).

Цель — отзывчивый интерфейс и небольшой объем полезной работы, а не нулевое число вызовов функции компонента. Рендер React и изменение DOM — разные события; измерять задержку взаимодействия и стоимость работы, а не только счетчик рендеров.

## 9. API, кеш и устойчивость к ошибкам

- Транспорт общий: базовый URL из проверенной конфигурации, обработка HTTP-статусов, отмена, согласованный формат ошибок. Обычного `fetch` достаточно, пока не доказана другая потребность.
- На границе проверять внешние данные схемой; TypeScript не валидирует полученный JSON. Не повторять тяжелую валидацию большого ответа при каждом рендере.
- Ключ кеша включает все параметры результата: филиал, категорию, фильтры, язык, страницу и при необходимости пользовательскую область. Секреты в ключи не включать.
- Для Query явно выбирать `staleTime`, `gcTime`, refetch и retry по классу данных. Каталог и статус оплаты не обязаны иметь одинаковую свежесть. Не использовать постоянный polling для всего приложения.
- Не повторять без разбора ошибки валидации и доступа. Повторение временных ошибок ограничено; для записи нужен отдельный анализ идемпотентности. Дефолты библиотеки нужно понимать, а не считать требованиями продукта: [TanStack Query defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults).
- Таймаут означает неизвестный результат операции, а не доказанное отсутствие заказа. После него уметь проверить состояние операции.
- Поиск: ограничить частоту запросов, отменять устаревшие или игнорировать их ответы; сохранять отзывчивый ввод. Debounce не применять к действиям, требующим немедленной обратной связи.
- Для каждого экрана определить initial loading, empty, error, retry, background refresh и недоступность сети. Фоновая ошибка не должна без необходимости удалять уже показанные данные.
- После мутации обновлять или инвалидировать только затронутые данные. Для optimistic update определить откат и защиту от гонок. Заказ и оплату не показывать успешными до серверного подтверждения.
- Общие ошибки имеют безопасный текст для пользователя и диагностический идентификатор. Не показывать stack trace, SQL и внутренние ответы провайдеров.
- Сначала параллелить независимые запросы; не создавать цепочки запросов из-за неудачного разбиения компонентов.

Для серверной части или отдельного backend обязательно согласовать контракт: схемы, коды ошибок, правила авторизации, пагинацию, идемпотентность и совместимость версий. При большом API рассмотреть генерацию типов из OpenAPI; не писать параллельно несколько несогласованных описаний вручную.

## 10. Каталог, корзина, оформление и платежи

Эти правила обязательны, если соответствующие функции входят в продукт.

- Денежные суммы хранить в целых минимальных единицах валюты с явной валютой. Правила округления едины; форматирование выполнять отдельно через `Intl`.
- Позицию корзины идентифицировать товаром, вариантом и выбранными опциями. Разные варианты не должны случайно объединяться.
- Количества имеют серверные границы; исключены отрицательные значения, дроби там, где они недопустимы, переполнение и чрезмерные размеры заказа.
- До создания заказа сервер пересчитывает цену, скидки, доставку, доступность, минимальную сумму и филиал. Клиентская сумма предварительная. При изменении условий показать разницу и получить подтверждение нового итога.
- Смена филиала, адреса или способа получения требует повторной проверки корзины и доставки. Не удалять позиции молча; объяснить, что изменилось.
- Часы работы, предзаказ, даты и сроки рассчитываются в часовом поясе бизнеса, а не по часам телефона. Обрабатывать границу суток и изменение графика.
- Создание заказа защищается от повторов на сервере: ключ идемпотентности привязан к одной попытке, пользовательской области и составу запроса; хранится результат, есть защита от конкурентных дублей. Повтор с тем же ключом и другим содержимым отклоняется.
- При повторе после таймаута использовать ту же попытку, а не генерировать новый ключ. Двойной клик блокировать и на клиенте, но этого недостаточно.
- Цена или наличие могут измениться между проверкой и сохранением: сервер выполняет нужные проверки и фиксацию согласованно, с транзакцией или подходящим механизмом резервирования.
- Платежи проводить через проверенного провайдера. Не собирать и не хранить карточные реквизиты в собственном React-приложении.
- Возврат с платежной страницы и deep link не доказывают оплату. Подтверждение — серверная проверка провайдера/webhook, его подлинности и допустимого перехода состояния.
- Повторные и пришедшие не по порядку webhook не создают повторное списание/заказ и не возвращают завершенный платеж в старое состояние.
- Заказ и платеж — связанные, но отдельные процессы. Должен быть сценарий восстановления, если пользователь закрыл страницу после оплаты или связь прервалась.

Критическую логику вынести в чистые функции модели, проверять на граничных значениях; сервер остается источником истины. Правила REST и контроля доступа: [OWASP REST Security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html).

## 11. Производительность, списки и анимации

### 11.1. Как измерять

Проверять production-сборку на согласованном слабом телефоне и замедленной сети. Лабораторные замеры воспроизводимы: фиксировать устройство/профиль, маршрут, объем данных и одинаковые условия. После запуска дополнять их реальными пользовательскими метриками.

Целевые Core Web Vitals: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1 на 75-м процентиле, отдельно для мобильных и компьютеров. Это полевые цели, а не обещание, что один Lighthouse-прогон доказывает качество: [web.dev Web Vitals](https://web.dev/articles/vitals).

Начальные внутренние ориентиры для обсуждения: до 250 KiB gzip клиентского JS и до 50 KiB gzip CSS для первого публичного маршрута, без отложенных частей. Это проектные бюджеты, не отраслевой стандарт. Подтвердить их на первом рабочем экране; при необходимости обоснованно изменить и закрепить в CI. Отдельно учитывать изображения, шрифты, сторонние скрипты и серверное время.

Для заметных изменений записывать сравнение до/после: задержка открытия корзины, ввод в форме, стоимость изменения количества, прокрутка каталога. Если несвязанные карточки выполняют дорогую работу при изменении одной позиции, найти причину подписок и props, а не подавлять симптом.

### 11.2. Списки и виртуализация

Начинать с обычного списка, пагинации или разумной порционной загрузки. Не задавать магический порог «100 элементов — всегда виртуализировать»: стоимость зависит от карточки, DOM, картинок и устройства. Проверять объем, ожидаемый в эксплуатации, и запас роста.

Виртуализацию вводить, если измерения показывают проблемы с количеством узлов, временем рендера или прокруткой. При необходимости использовать [TanStack Virtual](https://tanstack.com/virtual/latest/docs/introduction).

Обязательно проверить стабильные ключи, оценку и изменение высоты, overscan, адаптивное число колонок, resize, фильтрацию, восстановление прокрутки и возврат назад. Состояние редактируемой строки не должно теряться при размонтировании. Фокус не должен исчезать при прокрутке; accessibility, поиск по странице и переходы к категориям требуют отдельной проверки.

Для публичного каталога заранее решить, какой HTML доступен поисковику. Виртуализация оставляет часть элементов вне DOM и не является заменой SEO-стратегии. При загрузке страниц ограничивать и DOM, и объем удерживаемых данных: виртуализация сама по себе не ограничивает кеш.

### 11.3. Загрузка, медиа и движение

- Разделять код по маршрутам и тяжелым отложенным функциям. Не дробить каждый маленький компонент в отдельный сетевой запрос.
- Диалоги с тяжелым содержимым и карты загружать по необходимости. Prefetch применять выборочно, не скачивать заранее весь каталог и все экраны.
- Изображения отдавать в подходящем размере и формате, задавать размеры или соотношение сторон, использовать responsive-варианты. LCP-изображение не откладывать через lazy loading; остальные загружать по мере необходимости.
- Шрифты — только нужные гарнитуры, начертания и наборы символов, с предсказуемым fallback. Не подключать большую библиотеку иконок ради нескольких значков.
- Для коротких анимаций преимущественно использовать `transform` и `opacity`. Это не гарантия бесплатной отрисовки: проверять слои, площадь и нагрузку на GPU.
- Не анимировать постоянно большие размытия, тени, размеры и координаты через layout без причины. Не расставлять `will-change` на все элементы.
- Уважать `prefers-reduced-motion`, приостанавливать ненужное движение в фоне. Анимация не блокирует ввод и не является единственным носителем смысла.
- Не отправлять каждое движение мыши или кадр анимации в Zustand/React state. Для ручной покадровой работы использовать подходящий механизм с очисткой и контролем частоты.
- Сторонние карты, аналитика и виджеты имеют свой бюджет; при необходимости откладывать до взаимодействия и учитывать требования приватности.

## 12. Адаптивность, формы и доступность

- Проектировать mobile-first, использовать Grid/Flex и общие токены цветов, отступов, размеров, скруглений и слоев. Не создавать произвольные дубликаты значений по всему проекту.
- Контрольные ширины: 360, 390, 768, 1024 и 1440 CSS px; дополнительно проверить промежуточные состояния, landscape, длинные подписи и увеличение текста. Окончательная матрица определяется аудиторией.
- Проверять реальные границы элементов: нет неожиданного горизонтального scroll, перекрытых кнопок, обрезанных цен и прыжков сетки при загрузке.
- Действия — `button`, переходы — ссылки. Всем полям — label; иконкам-кнопкам — доступное имя; ошибкам формы — связь с полем и понятное объяснение.
- Интерфейс работает с клавиатуры, имеет видимый фокус, достаточный контраст и не зависит от hover. Практический ориентир удобной области касания — около 44×44 CSS px, с учетом контекста и промежутков.
- Цель по доступности — [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/) для применимых критериев; это требует ручных проверок, а не только автоматического отчета.
- В сложных формах подписываться на конкретные поля и ошибки. Не наблюдать всю форму в корне без причины; `useWatch` и локальные подписки размещать близко к потребителю. См. [React Hook Form](https://react-hook-form.com/).
- Не ломать ввод масками, автоформатированием и валидацией на каждый символ. Проверять вставку, автозаполнение, экранную клавиатуру и ввод через IME.
- Отправка показывает процесс и результат. Ошибка сохраняет введенные данные; повтор возможен безопасно. Toast не заменяет ошибку рядом с полем.
- Уважать системный размер текста и масштабирование. Для мобильных оболочек отдельно проверить safe areas, системные панели и клавиатуру.

## 13. Безопасность по проекту

Для каждой новой функции кратко перечислить: какие данные входят, кому разрешен доступ, какой возможен ущерб, где проходит граница доверия и как проверяется защита. Учитывать браузер, API, сервер, сторонние сервисы и будущий native bridge.

### 13.1. Доступ и сессии

- Сервер проверяет аутентификацию и разрешение на каждое действие и объект. Скрытая кнопка, роль в Zustand или знание `orderId` не дают права доступа.
- Для входа, восстановления доступа, хранения паролей и криптографии использовать поддерживаемые проверенные решения. Не изобретать собственные протоколы; для административного доступа предусмотреть MFA и минимальные права. См. [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).
- Проверять доступ и для гостевых заказов: публичный последовательный ID не является достаточным подтверждением владения. Секретные ссылки ограничивать по назначению и сроку.
- Для обычного same-origin сайта по умолчанию рассматривать серверную сессию в `HttpOnly`, `Secure` cookie с подходящим `SameSite`. Выбор зависит от потока входа и развертывания; cookie не отменяет CSRF-защиту.
- Для изменяющих состояние запросов применять выбранную CSRF-защиту и проверку происхождения запроса. Не использовать GET для изменения данных. CORS сам по себе не является авторизацией или полной CSRF-защитой.
- Если мобильной оболочке нужны токены, определить отдельный проверенный поток, срок жизни, отзыв и защищенное нативное хранение. Не переносить долгоживущий токен в localStorage ради обхода cookie-проблем.
- После logout и смены пользователя не показывать приватные данные предыдущей сессии. Серверные/CDN-кеши не должны смешивать данные пользователей и филиалов.

Основа: [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

### 13.2. Ввод, вывод и секреты

- API валидирует типы, размер, длину, допустимые значения и права. Принимать только разрешенные поля; не записывать клиентский объект в модель базы целиком.
- Для базы — параметризованные запросы или корректное API выбранной ORM. Клиентская проверка Zod улучшает UX, но не заменяет серверную.
- Пользовательский текст выводить как текст. HTML из CMS/редактора очищать поддерживаемым sanitizer по разрешенному набору; не использовать `dangerouslySetInnerHTML` с непроверенным содержимым.
- URL из внешних данных проверять по схеме и назначению. Не допускать `javascript:`-ссылки, open redirect и произвольное получение сервером URL пользователя.
- Секреты не находятся в Git, клиентских env, bundle, sourcemap или логах. Значения с публичными префиксами вроде `VITE_*` / `NEXT_PUBLIC_*` считать доступными пользователю.
- Не запрашивать у пользователя пароли, ключи подписи и production-токены в чате. Использовать предназначенное для секретов хранилище и минимальные права.
- Ограничивать размер и тип загрузок на сервере; проверять фактическое содержимое по риску, генерировать безопасное имя и хранить вне исполняемой области. Не доверять расширению и MIME от клиента.
- Телефоны, адреса, токены и платежные сведения маскировать в логах и аналитике. Собирать только необходимые данные, определить срок хранения и удаление.

Основа для вывода недоверенных данных: [OWASP XSS Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html); для runtime-схем: [Zod](https://zod.dev/).

### 13.3. Эксплуатация и злоупотребления

- Для сетевого обмена в production использовать HTTPS. Не отключать проверку сертификатов, не оставлять отладочные обходы и wildcard-доступ с credentials.
- Настроить CSP, ограничение встраивания через `frame-ancestors` и подходящие security headers для выбранной схемы размещения. Сначала проверить совместимость с платежами, SSR и сторонними сервисами; не добавлять `unsafe-*` только ради исчезновения ошибки.
- Ограничивать частоту и стоимость запросов на сервере: вход, OTP/SMS, промокоды, поиск и создание заказов. Клиентский cooldown легко обходится. CAPTCHA — дополнительный слой при необходимости, не замена лимитам.
- Использовать lock-файл, проверку зависимостей и секретов в CI. Результат dependency audit оценивать по достижимости и риску; не запускать автоматическое несовместимое обновление всех пакетов.
- Изменения платежей, прав доступа и персональных данных проходят отдельное ревью и негативные тесты. Найденная критическая уязвимость не откладывается под формулировкой «это MVP».
- Перед публичным запуском проверить восстановление резервных копий, доступы к окружениям и процедуру отзыва скомпрометированных ключей. Для значимого риска нужен отдельный аудит; линтер не доказывает безопасность.

## 14. Будущие Android и iOS: что заложить сейчас

### 14.1. Общая архитектура

Основной кандидат — [Capacitor](https://capacitorjs.com/docs): веб-интерфейс остается на React, нативные возможности подключаются плагинами. Ionic UI не обязателен. Собственные оболочки на Kotlin/Swift выбирать при конкретном ограничении, которое не закрывает поддерживаемый runtime.

Не переписывать интерфейс на React Native только из-за появления мобильного этапа. Это отдельная архитектура UI и отдельное решение, а не обязательное продолжение React-сайта.

Сейчас нужно:

- Держать бизнес-вычисления и контракты API независимыми от `window`, DOM, router и native API.
- Изолировать реальные платформенные операции в `shared/platform`: открыть внешнюю ссылку, поделиться, сохранить/выбрать файл, обработать возврат в приложение. Вводить конкретную операцию при ее первом использовании, а не универсальный bridge заранее.
- Определять native-среду официальным API runtime и проверять наличие capability. Ширина экрана, user agent и отсутствие hover не доказывают запуск в приложении. Любой такой признак не является проверкой безопасности.
- Предусмотреть web fallback или понятное сообщение при отсутствии возможности и отказе разрешения.
- Не размазывать платформенные условия по каталогу, корзине и формам. Native SDK импортировать за границей адаптера; серверная сборка не должна обращаться к браузерным API.

### 14.2. Как загружается мобильный интерфейс

По умолчанию для Capacitor рассматривать локально упакованные web assets и удаленное HTTPS API. Это дает контролируемую версию интерфейса и стартовый экран без загрузки всей страницы с сервера. Наличие локального UI не означает доступность каталога или отправки заказа без сети.

`server.url` в конфигурации Capacitor предназначен для live reload и не является рекомендованной production-схемой. Не оставлять его как способ «просто открыть сайт» в магазинной сборке. См. [Capacitor configuration](https://capacitorjs.com/docs/config).

Если выбирается собственная оболочка с удаленным HTTPS-сайтом, оформить отдельное решение: доверенные домены, поведение без сети, совместимость bridge и сайта, откат, контроль обновлений и требования магазинов. Удаленная загрузка и обновления web assets не дают права обходить ревью магазина или незаметно менять назначение приложения.

Не рассчитывать, что серверный Next.js runtime работает внутри локальной оболочки. Выбранный в разделе 3 профиль должен иметь реально проверяемую клиентскую сборку и маршрутизацию.

### 14.3. Навигация и жизненный цикл

- Общие стабильные маршруты и идентификаторы для сайта и приложения. Deep link открывает конкретный экран и проходит валидацию; наличие ссылки не дает доступ к заказу.
- Для внешнего входа и платежей использовать поддерживаемый провайдером поток через системный браузер/сессию авторизации или официальный SDK. Не считать произвольный embedded WebView допустимым для всех провайдеров.
- Поддержать Android App Links и iOS Universal Links с проверкой владения доменом. Холодный и теплый старт обрабатывать без повторного выполнения действия. См. [Capacitor Deep Links](https://capacitorjs.com/docs/guides/deep-links).
- Android Back: сначала активный диалог, затем история экрана; выход с корневого экрана — по согласованному UX. Не перехватывать кнопку глобально так, чтобы ломать системные жесты и поля ввода.
- После background/resume проверять актуальность сессии, корзины и статуса заказа. Не обещать, что JavaScript-таймеры продолжают работать в фоне.
- Обрабатывать завершение процесса ОС и восстановление. Несохраненная память может исчезнуть; повторное открытие не должно заново создавать заказ.
- Снимать listeners при смене жизненного цикла; не дублировать их при каждом открытии экрана. Для событий использовать возможности [Capacitor App API](https://capacitorjs.com/docs/apis/app).

### 14.4. Хранение, сеть и безопасность оболочек

- Cookie, CORS и origin локального приложения проверить отдельно от браузера. У iOS и Android могут различаться схемы origin и политика хранения. Не исправлять это отключением защиты или разрешением всех origins.
- Нативные HTTP/cookie-плагины подключать только при необходимости, с проверкой их влияния на текущий транспорт и сессии. Не включать глобальную подмену fetch случайно.
- Для секретов при токенной модели использовать Keychain/Keystore через проверенное решение; обычные Preferences и localStorage не считать защищенным хранилищем секретов.
- Bridge предоставляет только небольшой разрешенный набор операций с проверенными входами. Не создавать `eval`, выполнение произвольного JS, открытие любого URL, чтение любого файла или вызов произвольного native-метода.
- Не загружать недоверенные страницы и фреймы в контекст с привилегированным bridge. Проверять источники сообщений; для custom bridge определить версию контракта, таймауты и совместимость.
- Проверять схему, точный host и назначение URL, включая redirect и глубокие ссылки. Внешние сайты открывать вне привилегированного WebView. Сетевые HTTP-обходы, mixed content, игнорирование SSL-ошибок и production-debugging запрещены.
- Ссылки `tel:`, карты, банковские приложения, скачивания, file input и `window.open` требуют проверки в обеих ОС. Браузерный успех не доказывает наличие native-обработчика или сохранение файла.

Для custom Android bridge базовые ограничения описаны в [Android WebView security](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges). Привилегированные операции и минимальные разрешения требуют отдельного анализа для обеих ОС.

### 14.5. Мобильный UX и выпуск

- Safe areas и системные панели: не учитывать отступ одновременно в native-контейнере и CSS. Проверить нижнюю кнопку заказа и верхнюю навигацию.
- Экранная клавиатура не закрывает активное поле и отправку; диалог прокручивается; повороты экрана, zoom текста и жесты работают ожидаемо.
- Слабая сеть, offline, возврат из банка, истечение сессии и отказ разрешений имеют понятные состояния. Заказы и платежи по умолчанию не ставятся в скрытую offline-очередь.
- Push, геолокация, камера и доступ к файлам добавляются только под согласованный сценарий, с минимальными разрешениями. Не просить все разрешения на первом запуске.
- API поддерживает согласованное окно старых версий приложений. Сайт обновляется быстро, установленная оболочка — не у всех одновременно. Ломающие изменения API требуют миграции и периода совместимости.
- Версии web assets, API-контрактов и native-сборок различимы в диагностике. Обновление и откат не повреждают сохраненную корзину.
- iOS-сборка требует поддерживаемого macOS/Xcode-окружения и подписания; работа на Windows не подтверждает сборку и поведение iPhone. Проверять актуальные требования перед этапом сборки: [Capacitor iOS](https://capacitorjs.com/docs/ios).
- Оболочка должна иметь полезный завершенный пользовательский опыт. Простая переупаковка сайта может не пройти требования Apple 4.2; проверять актуальные правила перед проектированием мобильного этапа и перед публикацией. Нативные функции сами по себе не гарантируют приемку: [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/#minimum-functionality).
- Перед выпуском также проверить актуальные требования Google Play, SDK, privacy-декларации, разрешения и правила платежей по фактическому типу продукта: [Google Play Functionality](https://support.google.com/googleplay/android-developer/answer/9898783). Не переносить платежную схему физических товаров на цифровые покупки автоматически.

## 15. Тесты и контроль качества

Тесты защищают важное поведение и риск, а не количество строк. Не тестировать каждую обертку и не фиксировать внутреннюю реализацию snapshots ради отчета.

### 15.1. Минимальная полезная защита

- Чистая логика: корзина, округление, варианты товара, лимиты, смена филиала, миграции persist и переходы состояния.
- Компоненты: ввод и валидация формы, Dialog и фокус, loading/error/empty, disabled/pending, работа селекторов на важных границах.
- Контракты: поврежденные ответы API, несовпадение схемы, коды ошибок и отсутствие доступа. Моки не заменяют проверку реального контракта.
- Сквозные сценарии: каталог → карточка → корзина → изменение количества → оформление; отдельные тесты повтора, ошибки и восстановления.
- Безопасность: чужой заказ, подмена цены/роли, недопустимые поля, повтор отправки, небезопасные ссылки и выход из сессии.
- Для платформенного кода: браузерный fallback и отдельная проверка Android/iOS. Playwright WebKit не заменяет WKWebView на реальном iPhone.

Платежи, SMS и другие побочные действия тестировать на sandbox/тестовых учетных данных. Не оформлять реальные заказы и не отправлять реальные сообщения без явного разрешения.

### 15.2. Проверки перед завершением кодовой задачи

Обязательны ESLint, проверка типов, релевантные тесты и production build. Рекомендуемый контракт команд проекта: `lint`, `typecheck`, `test`, `test:e2e`, `build`. Их фактические команды и окружение зафиксировать в README и package scripts; не утверждать, что несуществующая команда запускалась.

Для существенных и критичных изменений дополнительно обязательно независимое ревью по разделу 16.6. Проверки отдельных исполнителей не заменяют проверку объединенного кода.

В ESLint включить подходящие правила TypeScript, React Hooks, доступности и границ импортов; при TanStack Query — его правила по необходимости. React Compiler diagnostics учитывать при включенном Compiler. Не отключать правило без локального обоснования. Новые предупреждения не игнорировать; старый долг фиксировать отдельно.

После изменения проверить:

1. Сам измененный сценарий и негативные состояния.
2. Потребителей компонента, общую оболочку, связанные selectors, API и стили.
3. Соседние ключевые сценарии: навигация назад, восстановление корзины, формы, авторизация.
4. Согласованную матрицу размеров и минимум одно слабое целевое устройство для изменений производительности.

После успешных проверок повторять их только при новых изменениях, сбое или конкретном нерешенном риске. Для правки Markdown без JS/TS-кода ESLint приложения не является применимой проверкой: проверить структуру, ссылки, согласованность и отсутствие секретов; явно сообщить область проверки.

## 16. Разработка с ИИ: анализ, вопросы и инструменты

### 16.1. До изменения кода

1. Прочитать действующие `AGENTS.md`, `CLAUDE.md`, `CHANGES.md`, README и локальные инструкции затрагиваемого модуля. Не изменять пользовательские незавершенные правки без необходимости.
2. Найти аналогичные изменения и существующие компоненты. При наличии графа сначала использовать Graphify по правилам ниже.
3. Кратко пересказать ожидаемый результат, затронутые модули, ограничения и проверяемые критерии приемки. Отделять подтвержденные факты от допущений и открытых вопросов.
4. Выявить спорные решения, пробелы, угрозы безопасности и влияние на браузер/будущие оболочки. Если формулировка допускает несколько существенно разных трактовок, показать их и рекомендовать вариант, не выбирать молча. Если есть более простое подходящее решение — прямо предложить его и объяснить цену компромисса.
5. До реализации задать уточняющие вопросы по неизвестным существенным условиям, желательно одним коротким раундом с рекомендуемыми вариантами. Уже полученные ответы учитывать и повторно не спрашивать.
6. Если существенных неизвестных нет, явно назвать допущения и продолжить в согласованном объеме. Не придумывать формальные вопросы ради самого факта вопроса.
7. По блокирующим вопросам дождаться ответа; параллельно можно выполнять независимое чтение и анализ. Молчание не считать подтверждением архитектуры, публикации или необратимого действия.

Если пользователь сказал «пока только обсудим» или «код не меняй», ограничиться анализом и согласованием. Не менять задачу на более широкую без основания. Для обратимой рутинной реализации в уже согласованном объеме не запрашивать повторное разрешение.

### 16.2. Grilling / grill-me

Перед работой проверить доступные skills. В данной среде соответствующий навык называется `grilling`; название `grill-me` может быть другим навыком или псевдонимом в другой установке. Не утверждать, что skill запускался, если он недоступен.

Для новой архитектуры, неоднозначной крупной функции или по прямому запросу использовать установленный навык критического интервью. Сначала прочитать его `SKILL.md` и соблюдать реальную процедуру: вопросы по зависимым решениям, рекомендуемые ответы, ожидание ответов и согласование понимания, если этого требует навык. Не заменять интервью формальным списком без учета ответов.

Для небольшой согласованной правки достаточно короткого анализа рисков; не запускать длинное интервью по умолчанию. Если обязательный skill отсутствует, сообщить об этом и согласовать допустимую замену, не изображая его использование.

### 16.3. Graphify

- Когда есть `graphify-out/graph.json`, вопрос о кодовой базе начинать с `graphify query "<вопрос>"`.
- Для связи модулей использовать `graphify path "<A>" "<B>"`, для понятия — `graphify explain "<понятие>"`.
- Для широкой навигации при наличии использовать `graphify-out/wiki/index.md`; большой `GRAPH_REPORT.md` читать только когда более точного поиска недостаточно.
- Проверять вывод графа в актуальном исходном коде. Граф может быть неполным или устаревшим; не считать предположительную связь доказанной.
- Если графа нет, искать по исходникам и прочитать skill перед построением. Не строить полный граф всего окружения ради небольшой задачи.
- После изменения кода запускать `graphify update .` из правильного корня проекта и проверять результат. При отсутствии инструмента или сбое явно записать, что граф не обновлен; не подменять это ручной отметкой «готово».
- Не включать в анализ секреты, приватные данные, зависимости и сборочные каталоги. Служебные результаты хранить согласно правилам репозитория.

### 16.4. Во время и после реализации

- Делать минимальное законченное изменение. Не внедрять будущую архитектуру и абстракции без потребителя.
- Каждая измененная строка должна объясняться задачей или необходимой поддержкой ее решения: зависимостями, проверками и документацией. Не совмещать исправление с несвязанным рефакторингом, переименованием и форматированием. При необходимости сопутствующего изменения объяснить связь.
- Удалять импорты, переменные, функции и стили, ставшие неиспользуемыми именно из-за текущей правки. Ранее существовавший несвязанный мертвый код без запроса не удалять: сообщить о нем отдельно. Обнаруженные существенные риски и уязвимости также сообщать сразу, не скрывать под предлогом узкого объема задачи.
- Проверять документацию для установленной версии библиотеки; не выдумывать API, команды, ответы сервера и результаты тестов.
- В ходе работы коротко сообщать о существенных находках и изменении решения. Ранние проблемы показывать сразу.
- Проверить соответствие стилю проекта, логические противоречия, переходы состояний и побочные эффекты в связанных файлах.
- После проверок добавить запись в CHANGES и при изменении кода обновить Graphify.
- Финальный отчет: что изменено, почему, что реально проверено, что не проверено и какие ограничения остаются. Не приравнивать build к проверке на устройстве или публикации в магазине.
- При делегировании кратко указать разделение работы, область независимого ревью, результат общих проверок и оставшиеся замечания. Не выдавать самопроверку исполнителя за независимое ревью.
- Оценить результат от 1 до 10 по полноте, простоте, корректности, производительности и проверяемости. Если ниже 7 — самостоятельно улучшить доступные части и объяснить улучшения. Оценка не отменяет блокирующую ошибку и не заменяет тесты.
- Commit, push, публикация и реальные внешние действия требуют явного разрешения пользователя. Предыдущая разрешенная операция не дает бессрочного разрешения на следующие.

### 16.5. От запроса к проверяемому результату

До реализации перевести пожелание в наблюдаемое поведение и способ проверки. Формулировки «сделать правильно» и «чтобы работало» сами по себе недостаточны.

| Запрос | Проверяемая цель |
| --- | --- |
| Добавить валидацию | Допустимые значения принимаются, недопустимые отклоняются с понятной ошибкой; проверены согласованные границы |
| Исправить ошибку | Сначала воспроизведен сбой, затем тот же сценарий проходит после исправления; для значимого повторяемого риска добавлен регрессионный тест |
| Провести рефакторинг | Поведение и публичный контракт сохранены; релевантные проверки выполнены до и после, исходные сбои отделены от новых |
| Ускорить взаимодействие | Названы устройство, объем данных и метрика; сравнение до/после подтверждает улучшение без потери функций |

Для многошаговой задачи дать короткий план в формате «шаг → ожидаемый результат → проверка». Масштаб плана и тестов соразмерен риску; небольшая правка не требует искусственного усложнения процесса.

Рабочий цикл: определить цель → реализовать → проверить → исправить выявленное → повторить затронутые проверки. Завершать по выполненным критериям, а не по факту написания кода. Если проверка недоступна или нужен ответ пользователя, явно назвать ограничение и следующий необходимый шаг; неподтвержденный результат не объявлять проверенным. Не повторять успешно завершенные проверки без причины — см. раздел 15.2.

### 16.6. Несколько агентов и независимое ревью

Количество агентов выбирать по риску и возможности разделить работу. Дополнительный агент должен давать независимую проверку или выполнять ограниченную самостоятельную часть задачи. Не создавать команду ради формального количества участников.

| Задача | Порядок работы |
| --- | --- |
| Небольшая локальная правка без значимого риска | Один исполнитель и соразмерные проверки |
| Существенная функция, сложная ошибка, изменение общего компонента или контракта | Исполнитель и отдельный агент для независимого ревью |
| Крупная задача с независимыми частями | Координатор, несколько исполнителей с разделенными зонами работы, затем интеграция и независимое ревью |

Изменения авторизации, прав доступа, платежей, персональных данных и native bridge требуют независимого ревью даже при небольшом объеме кода. Существенность определяется влиянием на поведение и потребителей, а не количеством строк. Для цепочки зависимых шагов несколько параллельных исполнителей обычно не нужны.

**Свежий контекст.** «Чистый агент» получает отдельную ограниченную задачу без автоматического наследования всей переписки и рассуждений автора. Координатор передает ему:

- Исходные требования, критерии приемки, подтвержденные решения и существенные ограничения.
- Применимые правила проекта, включая локальные инструкции и относящиеся к задаче записи CHANGES.
- Актуальные файлы, изменения и точное состояние кода, которое нужно проверить; при наличии — идентификатор ревизии.
- Контракты, связанных потребителей и доступные способы воспроизведения и проверки.
- Границы полномочий, известные исходные сбои и конкретный ожидаемый результат работы.

Не исключать важные требования ради «чистоты» контекста и не передавать секреты или лишние персональные данные. Ревьюер сначала формирует собственное заключение по требованиям и коду; объяснения автора использует затем для уточнения. Отдельный контекст не гарантирует отсутствия одинаковых ошибок и не означает изоляцию файловой системы.

**Разделение работы.** Координатор до параллельных правок согласует общие типы, API, владельцев файлов и точки интеграции. Один файл одновременно редактирует один назначенный исполнитель. При необходимости пересекающейся работы использовать последовательные правки или согласованные изолированные рабочие копии с последующей интеграцией. Изменение общего контракта сообщать затронутым участникам.

Операции с общим lock-файлом, установка зависимостей, генерация общих файлов и проверки, пишущие в один сборочный каталог, также требуют координации. Не запускать конфликтующие операции параллельно. Каждый исполнитель сообщает, что изменил, что действительно проверил и что осталось непроверенным; успешный отчет без проверки результата не является доказательством готовности.

**Независимое ревью.** Ревьюер не является автором проверяемого изменения и сначала работает в режиме чтения. Проверяет применимые риски: соответствие требованиям, логические ошибки и гонки, связанные сценарии, безопасность, подписки и производительность React/Zustand, браузерную и мобильную совместимость. Он может запускать разрешенные проверки без реальных внешних побочных действий. Исправления вносит назначенный исполнитель либо ревьюер после явной передачи владения соответствующими файлами.

Замечание содержит место в коде, условие возникновения, последствия, приоритет и доказательство: воспроизводимый сценарий, тест или конкретную цепочку логики. Отделять ошибки от предпочтений и предположений. Отсутствие замечаний допустимо; не придумывать проблемы ради отчета. Разногласия разрешает координатор по требованиям и проверкам, без голосования и автоматического принятия всех предложений ревьюера.

**Общая проверка после интеграции:**

1. Убедиться, что все части вошли в итоговый код и общие контракты согласованы.
2. Проверить объединенный сценарий и применимые негативные случаи; отдельно проверить взаимодействие частей, которые создавались независимо.
3. Выполнить ESLint, проверку типов, релевантные тесты и production build на итоговом состоянии по разделу 15.2. Уже выполненную проверку учитывать только если она относится к этому же состоянию кода и окружения.
4. Провести независимое ревью объединенного изменения, включая места интеграции и связанных потребителей. Отдельные ревью фрагментов не заменяют этот шаг.
5. Исправить подтвержденные ошибки; после существенных исправлений повторить затронутые проверки и соответствующую часть независимого ревью. Замечания вне объема задачи отметить отдельно, не расширять работу бесконечно.
6. Подтвердить критерии приемки, обновить документацию и при изменении кода Graphify. За итоговую совместимость и честность отчета отвечает координатор; при небольшой задаче он может совмещать координацию и реализацию, сохраняя независимого ревьюера там, где он обязателен.

Если независимый агент недоступен, прямо сообщить об этом и выполнить доступные дополнительные проверки. Для задачи, где независимое ревью обязательно, его отсутствие остается незакрытым критерием; самопроверка не заменяет его молча. Не заявлять об участии агента или выполненной проверке, которых не было.

Начинать с минимального полезного состава, обычно исполнителя и ревьюера для существенной задачи. Расширять команду при появлении самостоятельных направлений; ограничивать вложенное делегирование. Оценивать качество, время и расход ресурсов: несколько агентов не гарантируют ускорения и не отменяют тесты или контроль пользователя над публикацией.

Справочно: [OpenAI о разделении задач и отдельных контекстах](https://developers.openai.com/api/docs/guides/responses-multi-agent), [роль Code Review как дополнительной проверки](https://developers.openai.com/blog/custom-code-review-rules-for-codex). Обязательность ревью и порядок интеграции выше — правила нашего проекта.

## 17. Доставка, диагностика и документация

- Один package manager, один lock-файл, зафиксированные поддерживаемые версии Node и инструментов. Чистая установка и production build должны воспроизводиться в CI.
- Раздельные dev/staging/production-конфигурации. `.env.example` содержит только имена и безопасные примеры; отсутствие обязательной конфигурации выявляется при старте/сборке.
- CI проверяет lint, типы, релевантные тесты, сборку, бюджеты и безопасность зависимостей. Проверки не отключаются ради зеленого статуса.
- На staging проверять реальные маршруты, HTTPS, кеширование, прямое открытие страниц, fallback ошибок и интеграции в тестовом режиме.
- У релиза есть понятный способ отката. Изменения API и базы по возможности обратно совместимы; миграция не должна ломать еще установленные мобильные версии.
- Для ошибок — безопасная диагностика с версией сборки и идентификатором запроса. Настроить наблюдение за неуспешным оформлением, оплатой и недоступностью API, а не только сбор JavaScript-ошибок.
- Service worker/PWA/offline-кеш не включать автоматически. При необходимости определить обновление, очистку старых кешей и исключение сессий, заказов и приватных ответов.
- README объясняет запуск, конфигурацию, проверки, сборку, размещение, архитектурные границы и открытые ограничения. Важное решение записывать кратко: контекст → варианты → выбор → последствия.
- CHANGES содержит решения и ограничения, а не только список косметических правок.

Формат записи CHANGES:

```text
дата → задача → причина архитектурного решения → список новых файлов →
список измененных файлов → оговорки: нюансы, зависимости, ограничения платформы
```

## 18. Критерии готовности и запреты

Задача готова, если выполнены согласованные критерии, обработаны относящиеся к ней ошибки и края, проверки пройдены, выполнено независимое ревью там, где оно обязательно, связанные сценарии не сломаны, новые зависимости обоснованы, документация актуальна, а непроверенные платформы названы прямо. Незавершенные существенные проверки обозначаются как ограничение результата; открытая блокирующая ошибка или обязательное непроведенное ревью не позволяют объявить задачу полностью готовой.

Не допускается:

- Считать любую рекомендацию «best practice» без объяснения ее пользы в данном проекте.
- Обещать максимальную скорость, полную безопасность или отсутствие переделок без измерений и ограничений.
- Переносить весь state в Zustand, весь каталог в props каждой карточки или все формы в корень приложения.
- Оборачивать все в memo, добавлять виртуализацию ко всем спискам и подключать тяжелую библиотеку ради одного эффекта.
- Делать один компонент на все бизнес-сценарии или дробить код ради формального лимита строк.
- Дублировать источник истины, доверять клиентской цене, роли, статусу оплаты или «секретному» public env.
- Отключать CORS/SSL, добавлять wildcard bridge и хранить долгоживущие токены в обычном storage ради обхода проблемы.
- Считать адаптивный сайт автоматически проверенным Android/iOS-приложением.
- Объявлять готовыми авторизацию, оплату, ESLint, устройство или Graphify, если соответствующей проверки не было.
