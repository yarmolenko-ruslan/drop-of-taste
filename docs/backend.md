# Локальный бэкенд

Текущее ТЗ и проверки: [spec-local-mvp.md](spec-local-mvp.md). Сервер работает только локально. `NODE_ENV=production` блокируется до настройки реального SMS, HTTPS, постоянной MongoDB и правил обработки персональных данных.

## Запуск без домена и внешнего сервера

В отдельных терминалах: `npm run dev:db`, `npm run dev:api`, `npm run dev`. `dev:db` запускает локальную MongoDB с поддержкой транзакций и хранит её файлы в `data/mongodb` внутри проекта. Данные переживают перезапуск API и самой базы. Для внешней MongoDB задайте `MONGODB_URI` в `.env` по примеру `.env.example`. Уже запущенную временную базу нужно один раз остановить и запустить заново, чтобы перейти на постоянное хранение.

API слушает `127.0.0.1:3001`, сайт Vite проксирует `/api`. При первом старте сервер добавляет 42 блюда/набора/соуса из текущих страниц с примерными ценами в копейках. Повторный старт не перезаписывает уже изменённые позиции.

## Готовые маршруты

| Маршрут                                                    | Назначение                                         |
| ---------------------------------------------------------- | -------------------------------------------------- |
| `GET /api/health`                                          | Проверка процесса API                              |
| `GET /api/catalog`                                         | Категории, блюда, примерные цены и новинки         |
| `POST /api/auth/request-code`                              | Запрос кода для российского мобильного номера      |
| `POST /api/auth/verify-code`                               | Проверка кода и установка `HttpOnly` cookie        |
| `GET /api/auth/me`, `POST /api/auth/logout`                | Проверка и отзыв сессии                            |
| `GET/PUT /api/profile`                                     | Личные данные и настройки уведомлений              |
| `PUT /api/profile/notifications`                           | Отдельное сохранение настроек уведомлений          |
| `PUT /api/profile/delivery-selection`                      | Сохранение выбранного адреса (`addressId`/`null`)  |
| `GET/POST /api/addresses`, `PUT/DELETE /api/addresses/:id` | Адреса владельца сессии                            |
| `POST /api/checkout/quote`                                 | Серверный расчёт тестовой корзины                  |
| `POST /api/orders`, `GET /api/orders`                      | Создание и чтение только своих тестовых заказов    |
| `POST /api/orders/:id/complete`                            | Тестовое действие: отметить свой заказ выполненным |
| `GET /api/checkout/config`                                 | Наличие тестовой оплаты ЮKassa                     |
| `POST /api/orders/:id/pay`                                  | Создание тестового платежа                        |
| `GET /api/orders/:id/payment`                               | Проверка статуса платежа у ЮKassa                 |

Случайный одноразовый код локального API возвращается в ответе запроса кода, показывается над полем ввода пять минут и также появляется в терминале; SMS не отправляется. Эта возможность включена только в локальном тестовом запуске. Коды хранятся как HMAC, сессии — как хеш случайного токена. Сессия и cookie истекают через семь дней после входа. Подтверждение входа требует согласия; версия согласия и время принятия сохраняются в записи пользователя. Лимиты запросов и попыток проверки находятся в MongoDB. Имя cookie задаётся общей настройкой для входа, профиля и заказов: `dev_session` локально, `__Host-session` в защищённом режиме. Изменяющие запросы с cookie требуют разрешённый `Origin`. Выбор и удаление выбранного адреса используют транзакции MongoDB; постоянная база для этого должна поддерживать транзакции (replica set). Сервер берёт цены из MongoDB, блокирует добавки без цены и повторное использование ключа заказа с другим составом. Изменение итоговой цены между расчётом и подтверждением требует нового расчёта. Заказы не передаются кафе, бонусы не начисляются; тестовая оплата доступна только при настройке ЮKassa.

## Тестовая оплата ЮKassa

Тестовая оплата включается только при наличии обеих переменных `YOOKASSA_TEST_SHOP_ID` и `YOOKASSA_TEST_SECRET_KEY` на сервере. Ключ должен быть от тестового магазина. Сервер создаёт платёж по сохранённой сумме заказа с постоянным ключом идемпотентности, проверяет флаг `test`, сумму и статус ответа ЮKassa. Клиент получает только адрес перехода на страницу оплаты; статус `succeeded` фиксируется после отдельной проверки через API. Заказ остаётся тестовым и не передаётся в кафе. Локальный сервер не принимает вебхуки. Для публичного запуска понадобится HTTPS-адрес уведомлений и подтверждение статуса через API.

## Панель администратора и iiko

Админка доступна только в локальном режиме по `/admin`. Вход использует отдельный пароль `ADMIN_PASSWORD`, срок сессии 12 часов, HttpOnly-cookie, проверку Origin для изменяющих запросов и ограничение попыток входа. Пароль не хранится в базе. Если переменная не задана, API создаёт временный пароль и показывает его в терминале. Ручные изменения пишутся в MongoDB; каталог и контент сайта читаются публичными маршрутами. Редакция текста согласия задаётся в панели и записывается при следующем входе посетителя. Изображения до 5 МБ загружаются в `public/uploads`. Для постоянного развёртывания понадобится постоянное хранилище файлов и резервное копирование БД.

Акции и бонус-коды сохраняются в MongoDB с точным временем начала и окончания. Процент самовывоза задаётся в акции; среди действующих применяется наибольший. Комбо и наборы исключены из скидок. Бонус-код даёт процентную или фиксированную рублёвую скидку на остальные блюда; со скидкой самовывоза он не суммируется, действует более выгодная. Фиксированная скидка ограничена стоимостью подходящих блюд. Минимум заказа для доставки 500 ₽ и бесплатная доставка от 1500 ₽ считаются по стоимости блюд до скидок. При создании заказа сервер проверяет код и сумму повторно. Заказ на 0 ₽ завершается без обращения к платёжному сервису. Остальные акции на странице информационные: скидка ко дню рождения и подарок к первому заказу пока не применяются автоматически к онлайн-заказам.

В журнале администратора видны старые и новые значения ручных изменений, изменения цены и доступности при импорте iiko и переходы статуса платежей. Для старых платежей без событий показывается их последний сохранённый статус.

Для iikoCloud нужны `appId` и `clientSecret` приложения с [портала разработчика](https://api.iiko.help/quickstart), `apiKey` организации из iikoWeb → Интеграции → API-ключи, `organizationId` и `externalMenuId`. Ключи задаются только в `.env` сервера. Сервер получает токен через `POST /api/v2/access_token` и внешнее меню через `POST /api/menu/v3/by_id` по [официальной инструкции](https://api.iiko.help/docs/guides/external-menu/). Импорт запускается вручную из админки и записывается целиком либо не записывается при ошибке. Он принимает только простые позиции с одной ценой и без обязательных модификаторов, добавляет их в отдельные разделы `iiko-*`, обновляет цену и доступность уже импортированных карточек. Пропавшие из следующей полной выгрузки iiko позиции становятся недоступными. Ручные названия, описания и фотографии у существующих карточек сохраняются. Стоп-листы iiko доступны отдельным [методом API](https://api.iiko.help/docs/guides/stop-lists/), но пока не синхронизируются автоматически. Заказы сайта остаются тестовыми и в iiko не отправляются. Без ключей кафе реальное подключение проверить нельзя.

## Следующие отдельные этапы

Для публичной работы нужны постоянная MongoDB с резервным копированием, домен и HTTPS, SMS-провайдер, реальные цены и доступность меню, зоны доставки, приём заказов сотрудниками, юридическая проверка страниц, оплата и журнал бонусных операций. Эти области нельзя включать снятием локального ограничения сервера.
